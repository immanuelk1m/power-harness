# `발전량 큐` 행 양식

워커는 `사양·지시` 칸을 그대로 작업 지시로 읽는다. 아래 대괄호 필드명을 바꾸지 말고 순서대로 모두 채운다. 모르는 값은 "미확인(워커가 시트·코드에서 확인)"으로 적는다.

목차: 공통 판단 요약과 결과 연결 → 열 → INCREMENT·COMBINE·PIVOT 본문 → 결과 기록 줄 → REPLAY → REPLICATE → ARCH·ARCH-STEP → 금지 문구.
이 문서에서 확정 챔피언을 비교 기준으로 쓰는 모든 항목은, 확정 run이 아직 없으면 초기 REPLAY를 기준으로 사용하고 그 상태를 표시한다.

## 공통 판단 요약과 결과 연결

INCREMENT·COMBINE·PIVOT·ARCH·ARCH-STEP은 아래 `[판단 요약]`을 `[가설·근거]` 다음에 넣는다. 다른 필드에 같은 설명을 길게 반복하지 않는다. REPLAY·REPLICATE는 전용 양식을 유지한다. 작성 규칙은 `decision-protocol.md`를 따른다.

```
[판단 요약]
- 관측 사실: <P/큐 ID, 계약, seed, 비교 기준, 관측값과 출처>.
- 주가설 H_A / 경쟁 설명 H_B: <각 설명과 아직 확인하지 못한 것>.
- 구분 관측: <중간 지표·계산 방법·관측 기간, H_A/H_B에서 예상되는 방향>. 진단용 라벨과 평가용 라벨의 용도를 구분한다.
- 선택한 개입: <한 변경, 유지할 조건, 가까운 대안보다 먼저 실행하는 이유>.
- 결과별 다음 행동: <지지 → 행동 / 반증·약화 → 행동 / 판별 유보 → 필요한 관측>.
- 큐 연결: <이 질문을 담당하는 기존 행과 차이, 다음 단계의 진입 조건>.
```

워커는 결과의 LB/REP 줄을 유지하고 뒤에 다음 요약을 쓴다. 다음 하네스가 이를 읽는다.

```
[가설 판정]
- 사전 질문 / 구분 관측의 실제값·경로 / 지지·약화·판별 유보 / 대안 설명의 잔여 가능성.
- 성능 판정: 현재 계약 기준 대비, 계보 직전 대비, 계보 최고 대비를 분리.
- 실행 상태: 완료 / 기술 실패 / 계약·구현 무효. 대기 시간과 학습 시간을 분리.
- 다음 선택: 유지·바꿀 대상, 닫을 수 있는 검정 범위, 남은 질문.
```

## 열
- `순서`: 비워 둔다.
- `ID`: `power-<inc|comb|pivot|rep|arch>-<짧은영문이름>-YYYYMMDD`. REPLICATE는 `power-rep-<대상 P id 소문자>-YYYYMMDD`, REPLAY는 `power-rep-<대상 P id 소문자>replay-YYYYMMDD`. ARCH·ARCH-STEP은 `power-arch-<계보>-s<N>-YYYYMMDD`. 시트 두 탭에 같은 ID가 있으면 안 된다.
- `항목`: `[INCREMENT|COMBINE|PIVOT|REPLAY|REPLICATE|ARCH|ARCH-STEP] <방법 이름> — <한 줄 요약>`
- `사양·지시`: 아래 본문(한국어, 3,000–8,000자 권장).
- `갱신 시각`: 추가한 시각(KST).

## `사양·지시` 본문 (INCREMENT·COMBINE·PIVOT)
```
[모드] INCREMENT | COMBINE | PIVOT

[기준 레시피]
- 확정 작업 챔피언(없으면 초기 REPLAY 기준선) <P id 3개>(현재 계약 seed-mean W <값>, seed <값/값/값>, G1/G2 <값/값>, 월별 <1–5월 값>). SKILL 1단계에서 시트 최신값으로 확정한 값을 쓴다. 기본값을 하드코딩하지 않는다.
- 코드·config: <research/runs/<P id>/config.json 또는 powerlab/<파일>>. 시트의 해당 P id 결과에서 확인한다.
- 대조군 = 이 기준 레시피를 같은 코드·같은 seed·현재 계약(첫 발행 컷오프, 수정 후 patch)으로 2025 평가창 전체에서 다시 돌린 결과다. 이미 있으면 그 P id를 쓴다.

[단일 변경]
- 기준 레시피에서 바뀌는 것 하나만 코드 수준으로 쓴다: 어떤 입력/특징/대상/학습 단위/정산 결정을 어떻게 바꾸는지, 새 함수의 입출력, 추가되는 variant 키.
- 바뀌지 않는 것을 명시한다(나머지 특징, 하이퍼파라미터, 그룹 구성, 사후보정).
- COMBINE: 결합할 변경들의 P id와 각 단독 결과를 적고, 결합 방식을 쓴다.

[가설·근거]
- 해결하려는 W 성분(그룹/월/피크 11–15시/고 SMP/흐린 날·강수/ramp/부분 관측 사이트)과 그 크기: 내부 수치로 쓴다.
- 검증할 미해결 가설을 한 문장으로 쓴다.
- 경쟁 설명을 최소 1개 적는다.
- 근거 종류: LITERATURE(제목·저자·연도·링크, 우리 문제에 옮기는 방식) 또는 MATH+PHYSICS.
- 물리 메커니즘(NWP → 일사 → PV 변환 → 집계 → 정산 중 어느 단계)과 수학적 추정량을 적는다.

[연구 가치와 정보이득]
- **새로 알게 되는 것:** 이 실험 전에는 구분할 수 없던 가설/상태.
- **성공 판정이 의미하는 것:** 어떤 가설의 신뢰도를 높이고 다음 큐에서 무엇을 우선할지.
- **실패 판정이 의미하는 것:** 어떤 메커니즘/정보원/표현의 우선순위를 낮추거나 닫을지.
- **기존 연구와의 직교성:** 기존 레시피·보정·특징이 보지 못하던 어떤 정보·표현·물리상태를 보는지.
- **병목 연결:** 현재 W 질량이나 오라클 headroom 중 어느 부분을 직접 조사하는지.
- 예상 W 개선률은 신뢰할 근거가 있을 때만 참고로 적는다. 수치가 없거나 작다는 이유만으로 후보를 탈락시키지 않는다.

[휴리스틱 검사]
- `references/heuristics.md` 자가 점검 3문항의 답.
- 이 변경에 들어가는 모든 값·요약·경계(학습 시작일, 창·patch 폭, 임계값, 시간대·월 bin, 군집 수, 고정 가중, 축소 상수, round 선택)를 나열하고 각각 "학습형(무엇이 어떻게 학습하는지)" 또는 "표준 정의(출처 인용)"로 표시한다. 사람이 정한 값이 하나라도 남으면 행을 만들지 않는다.
- 챔피언의 휴리스틱을 학습형으로 바꾸는 행이면, 바꾸는 휴리스틱(heuristics.md 범주 a–f)을 적는다.

[인과 가용성]
- 새로 쓰는 모든 입력의 발행·관측 시각과 발행 시각(전일 17:00 KST) 이전에 얻을 수 있었다는 근거.
- fit·전처리·그룹·보정은 2024-12-31 17:00 이전 라벨만. 2025 라벨·실현 SMP·target 시각 실측 기상 미사용. poison check.

[필요 데이터·자원]
- 데이터 ID(PW-xxx)와 로컬 경로, 새 데이터가 있으면 출처와 사용자 예외 근거. CPU 또는 GPU, 예상 시간.

[실험]
- 2025 평가창 전체(3,624h × 253개소) full run을 seed 0/1/2로 돌려 보호 평가기로 채점한다(`powerlab.cli run` 또는 같은 형식의 새 runner). smoke와 단일 fold 판정은 하지 않는다.
- 같은 기준 레시피 대조군 대비 seed별·평균 W, G1/G2 W, 월별 W, 피크 11–15시 W를 보고한다.
- 구현 중 고장은 고쳐서 끝까지 완수한다.

[채택 시]
- 작업 챔피언보다 평균 W가 1.5% 이상 낮고 모든 seed가 낮으면 이 run이 새 잠정 챔피언이 된다(1.5% 미만은 동률). 확정은 REPLICATE로 한다.
- run 시작 시 시트에서 확정한 현재 SOTA와 같은 계약에서 그 값을 재현 가능하게 넘으면 SOTA 갱신 후보로 기록한다. 특정 P id를 SOTA로 하드코딩하지 않는다.

[부분 개선 시]
- 기준 레시피 대비 평균 −0.8% 이상이고 3개 seed 모두 낮으면 "스택 후보"로 기록한다.
- 성능 개선 폭이 작더라도 사전 정의한 중간 정보 검정에서 중요한 가설을 판별했다면 `정보 획득` 결과로 별도 기록한다.

[실패 시 닫히는 축]
- 유효한 검정이 반증한 구현·입력·계약의 범위만 적는다. 판별 유보·기술 실패로는 축을 닫지 않는다. 모델 계열 전체를 닫으려면 별도 직접 근거가 필요하다.

[중복 검사]
- 시트 `발전량 연구`/`발전량 큐`와 evidence.md에서 가장 가까운 기존 행 2–3개의 ID(P/S/X/QUEUE)와, 메커니즘이 어떻게 다른지. smoke만으로 끝난 행이면 그렇게 적는다.
```

## 결과 기록 줄 (모든 모드 공통 — 워커가 결과 칸 첫 줄에 쓴다)
`LB| P=<s0 P id>,<s1>,<s2> base=<base P id> seeds=<s0,s1,s2> W=<a/b/c> mean=<m> d_base=<값,%> grp=<G1 W/G2 W> mon=<1월/2월/3월/4월/5월 W> type=<특징 블록 추가|후처리·보정|하이퍼파라미터|예측 대상 변경|구조·학습 단위|새 정보원|그룹·정산 결정|replay|replicate>`
W는 원 단위 정수 또는 M(10⁶원) 소수 하나로 쓰되, 한 줄 안에서 단위를 섞지 않는다.
ARCH·ARCH-STEP 행은 같은 줄 끝에 `lineage=<계보> stage=<N> d_prev=<직전 단계 대비 값,%>`를 붙이고, `base`에는 비교 대상인 확정 챔피언(없으면 초기 REPLAY) P id를 쓴다. `type`은 ARCH라는 모드명 대신 실제 변경 유형을 쓴다. 계보 직전/최고 P id와 seed별 차이는 결과 본문에 별도로 기록한다.
사양 끝에 "결과 칸 첫 줄에 위 `LB|` 줄을 쓴다"를 적는다.

## REPLAY 양식 (현재 계약 replay — 작업 챔피언 출발점)
```
[모드] REPLAY

[대상]
- 대상 레시피 <P id 3개>(계약 이전 seed-mean W <값>, seed <값/값/값>), config <research/runs/<P id>/config.json>.
- 계약 결함: <예: 산출물이 2025-01-01 00:00까지 fit, 수정 전 ctx7 patch>.

[단일 변경]
- 레시피의 모델·특징·하이퍼파라미터는 그대로 두고, 계약을 어긴 부분만 현재 계약으로 다시 만든다: 모든 산출물(그룹 구성, 표본 가중, 사후보정, affine)을 첫 발행 2024-12-31 17:00 이전 라벨로 재생성(기존 `research/cutoff_fi17/` 생성기를 쓸 수 있으면 쓰고, 수정 후 patch 코드로 OOF부터 다시 만들어야 하면 다시 만든다), patch는 현재 `powerlab/baselines.py` 코드로.
- 생성기에 들어 있는 기존 값(축소 상수, 군집 수 등)은 바꾸지 않는다.

[실험]
- 2025 평가창 전체 seed 0/1/2 → 보호 평가기. 대상 레시피(계약 이전)와 seed별 W 차이, G1/G2·월별 W를 보고한다.
- 결과가 계약 이전 run보다 나빠도 정상이다. 이 run이 현재 계약의 기준(작업 챔피언 후보)이다.

[결과 기록] 첫 줄 `LB| ... base=<대상 P id> type=replay`. 둘째 줄에 `comparator=<대상> contract=fi17+patchfix`.
[인과 가용성] 첫 발행 컷오프, poison check. [필요 데이터·자원] 대회 원자료만, CPU. [중복 검사] X0198(fi17 수리, 수정 전 patch), X0225(patch 결함).
```

## REPLICATE 양식
```
[모드] REPLICATE

[대상과 기준]
- 대상 <P id 3개>(원 seed 0/1/2 W, 평균, base 대비 %), 기준 <base P id 3개>(원 seed W).
- 재현 이유: 1.5단계 진단의 어떤 신호(H1/H2)와 수치 때문인지.

[단일 변경]
- 없음. 대상 레시피와 기준 레시피를 코드·특징·하이퍼파라미터 그대로 두고 seed 3, 4, 5로 두 run을 새로 돌린다. 원본 코드는 수정하지 않는다.
- 레시피가 seed를 fold·표본 인덱스로 쓰는지 먼저 확인한다. 그렇다면 무작위성만 바꾸는 동등한 seed 정의를 두 run에 똑같이 적용하고 기록한다.

[실험]
- 두 run 모두 2025 평가창 전체 seed 3/4/5 → 보호 평가기.
- 6-seed 짝 판정: d_k = W(대상,k) − W(기준,k), k=0..5. 확정 = mean(d)<0 이고 t ≤ −2, 또는 6개 모두 음수. 그 밖은 기각. 새 seed 평균 d ≥ 0이면 "우연"으로 기록.
- G1/G2·월별 짝 차이도 보고.

[결과 기록]
- 첫 줄 `LB| ... type=replicate`, 둘째 줄 `REP| target=<대상> base=<기준> d=<d0..d5> mean_d=<값> t=<값> verdict=<확정|기각>`.

[채택 시]
- 확정이면 대상이 확정 챔피언(또는 확정 스택 후보)이 된다. 기각이면 "노이즈 가능"으로 표시한다.

[인과 가용성] 원 실험과 동일. [필요 데이터·자원] 새 데이터 없음, 3-seed run 2개. [중복 검사] 원 실험 행 ID.
```

## ARCH / ARCH-STEP 양식 (아키텍처 전체 피봇, 계보 예산제)
```
[모드] ARCH (새 계보 s1) | ARCH-STEP (활성 계보의 다음 단계)

[계보 ID] <계보 이름>   [단계] s<N> / 6

[전체 구조]
- 입력 표현 → 모델 → 출력(사이트 또는 그룹의 2025 평가창 시간별 발전량)을 단계별로 쓴다. 챔피언 계열(사이트별 LightGBM/ExtraTrees + 그룹 합 + 사후보정)과 무엇이 근본적으로 다른지 한 줄로 쓴다.
- ARCH-STEP: 직전 단계(P id, 코드 `powerlab/arch_<계보>_*.py`)에서 바꾸는 것 하나만 코드 수준으로 쓴다.

[입력·데이터 파이프라인]
- 쓰는 source(PW-xxx)와 표현, 발행 시각 정렬 방법. 기존 데이터 로더·인과 특징 빌더 재사용은 허용한다.
- 금지: 챔피언 계열의 예측·잔차·OOF를 입력이나 타깃으로 쓰는 것, 챔피언 계열과의 블렌딩·앙상블.

[학습 설계]
```
